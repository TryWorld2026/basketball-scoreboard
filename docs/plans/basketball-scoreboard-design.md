# 篮球计分板 · 设计文档

日期：2026-09-24（2026-09-28 修订）｜ 状态：已实现并部署（score.tryworld.com.cn）｜ 项目：篮球计分板

---

## 1. 产品定位

**一句话**：校园班赛的官方记分牌——手机当遥控器，任何一块屏幕当大屏，打完自动出一张能甩进班群的数据卡。

**真实痛点**：班赛没有计分板，比分记在某个人的手机备忘录里，打完吵架"到底几比几"，第四节最后两分钟没人记得清犯规。产品价值全部押在**双端同步**和**大屏可读性**上，不押在功能数量上。

**目标用户**：班赛的记分员（学生，非专业）、场上球员、场边围观同学。

---

## 2. 已确认决策清单

| 决策点 | 结论 | 理由 |
|---|---|---|
| 使用场景 | 校园班赛现场，双端架构 | 唯一让产品"真有用"的场景 |
| 产品边界 | 单场闭环 + 赛后数据卡；预留赛事扩展 | 班赛90%需求在此；赛事系统（报名/赛程/积分榜）明确不做 |
| 统计深度 | 球队级为底，「记录球员得分」建赛时可选开关，默认关 | 省事的人直接打，想发数据卡的人勾上 |
| 规则默认值 | 4节×10分钟、单节团队犯规满5次罚球、每队3次暂停、24秒默认关、平局自动加时 | 班赛友好默认值，建赛时可改 |
| 视觉 | 转播风格 + 球队色彩驱动，纯 CSS 画 LED | 三米外看清比分是第一性能；每场界面由两队队色生成 |
| 同步 | 客户端只发"意图"，服务端原子算状态；1秒轮询 | 防并发丢分；比分晚1秒无感 |
| 时钟 | 不跑在服务端，存 `running+since`，各端本地推算 | 刷新/换机/断网重连不丢时钟 |
| 归零处理 | 自动蜂鸣+进节间休息，不等确认 | 学生记分员手忙脚乱，少一步是一步 |
| 撤销 | 只撤最近一步 | 误按都是刚发生的，多步历史诱发混乱 |
| 登录 | 不做。4位房间码即分享即加入 | 班赛搞账号体系是自嗨 |
| 防锁屏 | 控制端 WakeLock | 记分员不可能打一节亮一次屏 |
| 数据卡存图 | 纯前端 canvas 导出 PNG，不过服务器 | 这是"发班群"的嗨点，且不增加后端负担 |

**明确不做（YAGNI）**：赛事报名/赛程/积分榜/淘汰签表、球员篮板助攻等完整技术统计、多场地并轮、回放挑战、账号体系、WebSocket 长连接、历史比赛列表页（链接即档案）。

## 3. 核心流程

```
建赛（手机 30 秒）
  队名/队色/赛制/犯规上限/暂停数/24秒开关/球员名单开关
  → POST create → 房间码 4K7P + 二维码
        │
        ├─▶ 大屏（笔记本/电视扫码）→ GET /room/4K7P/display → 每秒轮询，只读
        │
        └─▶ 控制端（记分员手机）→ /room/4K7P/control
              比赛中所有动作 → POST apply{意图} → 服务端算状态 → 两端各自轮询到
              │
              └─▶ 结束比赛 → 状态锁定 → /room/4K7P/card 数据卡 → 存 PNG / 复制链接
```

## 4. 界面规格

### 4.1 视觉系统（转播风格）

- **背景**：`#0A0E1A` 深黑蓝。两队队色以斜切面板（`clip-path` 平行四边形）铺在左右，中央留出时钟区。
- **LED 数字**：纯 CSS 自绘七段数码管（每数字 7 个 `clip-path` 段，亮段带同色辉光，灭段 8% 透明度残留）。零字体文件、零图片，任何分辨率清晰。这是产品的视觉签名。
- **字体**：`system-ui` 粗体用于队名/标签；数字一律走 LED 组件。
- **状态色**：BONUS = 红色脉冲；暂停 = 琥珀色；归零 = 全屏红闪 2 次；信号弱 = 整体降饱和 + 灰角标。
- **色盲友好**：颜色永远配合文字标签（"主队/客队"+队名），不单独用颜色编码。
- 三张 AI 风格图（本地 `vibe_images/`，未纳入版本库）仅为方向参考，不进入产品。

### 4.2 建赛页 `/`

队名A/B（必填）+ 取色器（12 预设色板 + 自定义）；赛制 2/4 节 × 5/10/12/15 分钟；单节犯规上限（默认5）；暂停数（默认3）；24秒开关（默认关）；「记录球员得分」开关（默认关，开启后出现两队球员名单输入）。提交后进入**房间页**：大号房间码 + 二维码 + 两个按钮（打开大屏 / 打开遥控器）。

### 4.3 控制端 `/room/:code/control`（手机竖屏，单手拇指区）

```
┌─────────────────────────┐
│ 4K7P ●在线        ↩撤销 │
│ Q2  07:32     [⏸/▶]  ▶红│
├─────────────────────────┤
│ 🔴计算机1班        48   │
│ [张伟][李强][王芳]       │
│  +1    +2    +3         │
│  犯规+1      暂停-1      │
├─────────────────────────┤
│ 🔵软件工程2班     47    │
│  +1    +2    +3         │
│  犯规+1      暂停-1      │
├─────────────────────────┤
│ [下一节 ▶]   [🏁结束比赛]│
└─────────────────────────┘
```

- **球员 Chip 是选中态**：点某人高亮，此时 +1/+2/+3 记到该球员；再点取消回到球队级。选中态常驻可见防误按。
- 按钮 ≥56px、高对比（户外阳光下可读）；每次成功写入触发 `navigator.vibrate(15)` 震动反馈。
- 顶部状态条：连接状态（●在线 / ⚠N个待发送 / 冲突提示）+ 撤销按钮（撤完置灰 1 秒）。
- WakeLock 常亮；切后台自动让位，回前台重拿并立即同步。
- 键盘快捷键（笔记本当控制端时）：`空格` 开始/暂停，`Z` 撤销，`A/S/D` 主队+1/+2/+3，`J/K/L` 客队+1/+2/+3。

### 4.4 大屏展示端 `/room/:code/display`（16:9 投影优先）

```
┌──────────────────────────────────┐
│ Q2        07:32        ● 直播     │
│ ┌───────────┐     ┌───────────┐  │
│ │ 计算机1班 │48:47│软件工程2班│  │
│ │ ●●○ 暂停2 │     │ 暂停3 ●●● │  │
│ │ 犯规 3/5  │     │ 犯规 4/5  │  │
│ └───────────┘     └───────────┘  │
│   BONUS 红队罚球     ▶进攻 红     │
└──────────────────────────────────┘
```

只读、零操作。节间休息/暂停自动切全屏倒计时画面。已结束自动跳数据卡。**画面状态必须诚实（2026-09-28 加固）**：房间不存在/已归档显示错误面板——打错的房间码不能假装"等待开赛"；首次加载与重连有明确文案；超过 3 秒无响应时时钟冻结在最后可信值并挂「信号弱·最后更新 HH:MM」角标——服务端可能已被记分员停表/跳节，本地继续推就是假时间，冻结期也不触发归零蜂鸣。

### 4.5 数据卡 `/room/:code/card`（3:4，适合群聊）

终比分 + 获胜标记、每节得分流水、得分王（开启球员记录时）、三分对比、犯规对比、房间码水印。两个按钮：**保存图片**（canvas 导出 PNG）、**复制链接**。PNG 下方另有**操作记录**面板：按版本变化拉取 `/api/game?action=log`，逐条列出时间/动作/前后比分/操作者指纹——赛后吵架时的核对面（读不到审计不影响数据卡本身）。

## 6. 数据模型

主表 `games` 仍是一场比赛一行、整场状态一个 JSON 文档（读-改-写 + 版本号 CAS 的模型下，规范化拆表只会增加跨请求事务问题）；`action_receipts` 是与比赛行级联的幂等回执辅表，`action_log` 是与比赛行级联的操作审计辅表：

```sql
create table games (
  code        text primary key,            -- 4位房间码（字符集去 0O1I）
  status      text not null default 'setup',-- setup|live|break|timeout|finished
  version     integer not null default 0,   -- 每次写 +1，CAS 用
  state       text not null,               -- 见下（SQLite 存 JSON 文本）
  created_at  text not null,               -- ISO-8601 UTC 文本
  updated_at  text not null,
  controller_hash text,                     -- 控制凭证的 SHA-256（migrations/0002；NULL = 迁移前的老行，只读）
  recovery_hash text                        -- 控制找回码的 SHA-256（migrations/0005；补发时轮换）
);
-- 预留赛事扩展：以后加 tournament_id 列，不动结构

-- 幂等回执（migrations/0002 + 0003）：nonce 落地过就记一行，与状态写入同一个批处理。
-- 去重窗口不限长度，随比赛行级联删除（半途放弃局清理时一起走）。
create table action_receipts (
  code        text not null references games(code) on delete cascade,
  nonce       text not null,
  created_at  text not null,
  receipt_id  text unique,                 -- migrations/0003：本次 INSERT 的 attempt marker；老回执可为 NULL
  primary key (code, nonce)
);

-- 操作审计（migrations/0004）：每一次落地写一条——谁（凭证指纹，不明文）/何时/
-- 什么动作/比分从多少改成多少/当时时钟。与状态更新同一个批处理：CAS 输了就不记。
-- reset 重开不清日志（终局被擦掉这件事必须可查）；随比赛行级联删除。
-- 只记真落地：被规则拒的、幂等拦下的、无变化的动作都不留痕。
create table action_log (
  code        text not null references games(code) on delete cascade,
  seq         integer not null,            -- 落地后的 version，天然时间序
  actor       text not null,               -- 控制凭证 SHA-256 前 8 位（区分设备，不泄露凭证）
  action      text not null,               -- 意图 JSON 原样（含 nonce，可和补发对账）
  before_score text not null,              -- "24:22"
  after_score  text not null,
  clock_ms    integer not null,            -- 动作时刻的比赛时钟剩余（屏幕显示值）
  at          text not null,
  primary key (code, seq)
);
```

`state` 结构：

```jsonc
{
  "config": { "periods":4, "periodMinutes":10, "overtimeMinutes":5,
              "foulLimit":5, "timeouts":3, "timeoutSeconds":60,
              "shotClock":false, "shotClockSeconds":24,
              "trackPlayers":false, "breakSeconds":120 },
  "teams": [ { "name":"计算机1班", "color":"#1E4FD8", "score":48,
               "fouls":3, "timeoutsLeft":2,
               "periodScores":[12,14,13,9], "stats":{"pts3":6,"pts2":15,"pts1":6} }, ... ],
  "players": [ { "team":0, "name":"张伟", "points":15 } ],
  "clock":   { "mode":"game", "period":2, "running":true,
               "since":"…", "remainingMs":452300, "gameRemainingMs":452300,
               "timeoutTeam":null },
  "shot":    { "running":false, "since":null, "remainingMs":24000 },
  "possession": 0,
  "undo":    { /* 上一步快照：teams/players/clock/shot/possession，仅一层 */ },
  "startedAt":"…", "finishedAt":null, "winner":null
}
```

**时钟推算（各端一致）**：`mode=game` 且 `running` 时，显示值 = `remainingMs - (now - since)`；停止时显示 `remainingMs`。暂停/节间用 `mode` 切换，比赛时钟冻结在 `gameRemainingMs`。

## 7. 同步与动作模型

```
客户端                          Worker (handler)                  D1
  │ POST apply{code,version,意图} ─▶ 读 state+version
  │                                 CAS: update where version=期望
  │                                 0行受影响 → 重读重放（≤3次）→ 仍冲突返回409
  │ ◀─ 新 state+version ────────────┘
  │ GET get&code ─▶ {state, version, serverTime}   （两端各自每秒轮询）
   │ GET log&code ─▶ {entries}                      （赛后核对，按版本变化拉）
```

- **意图白名单**：`score{team,points,playerId?}`、`foul{team}`、`timeout{team}`、`clock_start/stop`、`shot_reset`、`possession{team}`、`period_next`、`clock_zero`（归零自动进节）、`undo`、`finish`、`reset`。未知动作 400。所有意图带客户端生成的 `nonce`。
- **`playerId` 类型门禁（对抗审查补）**：只接受字符串。`String(['张三']) === '张三'` 这种能穿透 JSON 的脏数据会被静默变成合法球员名，进而把分记到人头上。
- **24 秒不是装饰（对抗审查补）**：`shot_reset` / `possession` 在规则层一直存在却没有 UI 入口，等于没实现；同时进球后旧实现把 24 秒停死，而 `clock_start` 又因"已在跑"被拒，导致它永久冻结。现在开球即走、进球归满并继续走、归零蜂鸣自动重置，控制端有「↻ 24秒」和「⇄ 交换球权」两个入口。
- **撤销必须冻结时钟（对抗审查补）**：撤销快照若原样存绝对 `since`，撤销一次"停表"会让停表那段真实时间被当成比赛时间消耗掉——时钟在记分员看不见的地方向下跳。现在快照把运行中的时钟冻结成那一刻的显示值，撤销只回退数据，是否继续走由记分员显式按「开始」。
- **失败限流（对抗审查补）**：房间码可被遍历。按 IP 只统计失败请求（房间不存在/参数非法/冲突/凭证不符），正常轮询不计次；进程内计数，属尽力而为（见 README 已知边界）。
- **半途放弃局清理（对抗审查补）**：只清 `setup` 会让"建过赛、打了几下就走人"的房间永久留在库里。现在建赛时顺带清掉超过 7 天无写入的 `live/break/timeout` 行；`finished` 永久保留（数据卡链接要能长期打开）。
- **乱序响应保护（对抗审查补）**：轮询 GET 可能比刚发出的 apply 响应更晚到达。前端按 `version` 丢弃旧快照，否则比分会瞬态闪回。
- **幂等键（对抗审查补，2026-09-28 加固）**：户外丢包时客户端会补发同一意图，服务端按 `nonce` 去重——回执落 `action_receipts` 表，与状态写入同一个批处理；`receipt_id` 证明 UPDATE 使用的是**本次 INSERT** 的回执，旧回执不能满足 UPDATE。重复意图只记一次且不涨版本。去重窗口不限长度：旧实现把 nonce 塞进比赛 JSON 只留最近 30 条，双记分员场景下超过 30 次后续写入，补发就被挤出窗口、同一意图记两次分。没有这一条，一次信号抖动就能凭空多算 2 分。
- **模式门禁（对抗审查补）**：记分/记犯规只在 `clock.mode==='game'` 时接受——休息期按 +3 会静默记进下一节的流水，属于数据污染；叫暂停还要求 `status==='live'`，否则未开打就能烧掉一次暂停。
- **无变化不写库**：应用后状态与之前等价（如重复上报归零）直接返回当前状态，不涨版本，避免多端同时上报造成无意义 CAS 冲突。
- **操作审计（对抗审查补，2026-09-28 加固）**：每一次落地写一条 `action_log`——谁（控制凭证 SHA-256 前 8 位，不明文）/何时/什么动作/比分从多少改成多少/当时时钟。和状态更新走同一个批处理，CAS 输了就不记，不存在"状态变了审计没记"。`action=log` 与读比分同级（房间码即读）：班里任何人拿到码都能核对记录，公开才有人信——这是它防"打完吵架"的方式。只记真落地：被规则拒的、幂等拦下的、无变化的动作都不留痕；`reset` 重开不清旧日志。赛后数据卡页有「操作记录」面板按版本变化拉取。
- **入口安全响应头（对抗审查补，2026-09-28 加固）**：控制端可被 iframe 嵌入做 UI redressing（诱骗记分员点 +3）。Worker 入口对所有响应（API 与静态）统一加 `frame-ancestors 'none'` + `nosniff`——这个应用没有任何被合法嵌入的场景。快捷键另外过滤 Ctrl/Meta/Alt，避免系统快捷键被当成记分动作。
- **服务端到点推进（对抗审查补，2026-09-28 加固）**：之前「时钟归零」完全依赖控制端在线——记分员锁屏、杀后台、被叫走、手机没电，任何一样发生，节间休息/暂停倒计时就永远停在 00:00。现在每分钟 cron 扫 live 比赛，把已归零的推进一步；实现上直接调和服务端 `applyAction` 同一套 `clock_zero` 规则（不另写分支，行为逐字一致），「无变化不写库」就是幂等闸门，和记分员自己上报撞车时 CAS 保证只有一个生效。审计 actor 记 `cron`。**cron 只推进时刻，不代替人操作**：开表、记分仍然只有控制端能发。
- **控制权补发（对抗审查补，2026-09-28 加固）**：「创建比赛的那台手机丢了」此前无解——只能重建比赛、丢掉整场记录，而丢手机（换机/清缓存/被借走）是现场最高频的事故。现在建赛时随控制令牌一起签发 8 位找回码（明文只回一次，库里只存 SHA-256），凭「房间码 + 找回码」在任意设备换发新的控制令牌。**换发即换锁**：新令牌 + 新找回码同时轮换，旧令牌与旧找回码立即作废——当初截屏流落到班群里的旧码从此失效，救援能力却不断（新码可再次补发）。补发不碰比赛状态（比分/时钟原样，版本 +1 以便审计落盘），失败计入限流器（找回码是第二个 Secret，不能白试），审计 actor 记 `recovery`。房间页把找回码单独一块展示 + 一键复制，并明说「只存在这台设备上没用，要带走」。
- **休息中按"下一节"= 提前结束休息**（班赛休息期常提前开打），不再报错。
- **服务端规则引擎**：得分→队/球员分数+节流水+三分计数+进攻箭头转向；犯规→满 `foulLimit` 置 BONUS；`clock_zero`→进节间休息（新一节犯规清零）；末节平局→自动加时，**末节分出胜负必须结束**（不得无限加时）；`finish`→锁定、算 winner（平局为 null，不误判主队）。
- **严格整数**：`team`/`points` 只接受真正的整数，拒绝 `null`/`"2"`——`Number(null)===0` 会把脏输入静默变成"主队加 0 号位"。
- **断网（2026-09-28 加固）**：控制端动作进本地队列（localStorage 持久化，上限 50，满额拒绝新动作并明说），恢复后按序补发；**只有"已发生的事实"才配排队**——得分/犯规/球权与幂等的归零、24 秒重置。撤销、clock 迁移、终局类的含义依赖发生的时刻：迟到的撤销会吃掉队友后来的操作，迟到的结束会在错误的比赛上锁分，这些必须联网才发。大屏 >3 秒无响应显示"信号弱·最后更新 HH:MM"并冻结时钟显示。
- **房间码**：字符集 `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`（去易混 0O1I），4 位 ≈ 100 万组合，创建时查重。
- **清理**：平台无 cron。创建新房间时顺带删除 `status=setup 且超 24h` 的废弃房间；已打完的房间永久保留（数据卡链接要能长期打开）。

## 8. 异常状态矩阵

| 状况 | 表现 | 恢复 |
|---|---|---|
| 房间码不存在 | "房间不存在或已归档"+新建引导 | 检查码/新建 |
| 控制端断网 | 角标"⚠N个待发送"，按钮仍响应（本地乐观+队列） | 恢复按序补发 |
| 大屏断网 | 灰角标"信号弱·最后更新 19:42"，时钟静止不显示假时间 | 轮询恢复自动续 |
| 时钟归零 | WebAudio 合成蜂鸣+全屏红闪，自动进节间休息 | 休息归零自动进下一节；控制端不在场时 cron 一分钟内补推 |
| 时钟归零但控制端不在场（锁屏/杀后台/没电） | 大屏照常蜂鸣，服务端 cron 到点推进，不停在 00:00 | 控制端回来后自然续上 |

| 存图失败 | 提示"请截图保存" | 降级可用 |

## 9. 技术选型与部署契约

**部署平台变更记录（2026-09-24）**：首版按 Qoder Sites（静态 + Edge Function + Supabase 适配器）实现并本地验证通过，但平台侧建站请求持续返回通用失败，云资源无法分配；同日改投 **Cloudflare Workers + D1** 并完成部署与线上验证。规则引擎与前端一行未动，只替换了数据访问层——这验证了当初"handler 只依赖注入的 store 接口"的分层是对的。

- **前端**：纯静态 SPA（原生 ES modules，无框架无构建），目录 `public/`，由 Workers Assets 托管，SPA 回退用 `not_found_handling: single-page-application`。
- **服务端**：`worker/index.js` 为 Workers 入口，`/api/*` 走业务 handler，其余交给静态资源绑定；入口统一加安全响应头（`frame-ancestors 'none'` + `nosniff`）。业务层 `worker/handler.mjs` 只依赖 store 接口（`getGame / insertGame / casUpdateGame / casUpdateGameWithReceipt / getLog / deleteStaleSetup / deleteAbandoned`）。
- **数据库**：Cloudflare D1（SQLite）。整场状态一个 JSON 文本列 + `version` 列；幂等回执在 `action_receipts` 辅表；操作审计在 `action_log` 辅表（与状态更新同一个批处理）；并发写用 `UPDATE ... WHERE code = ? AND version = ?` 的**影响行数**判定 CAS，这是真实 SQL 语义，不是内存假库的模拟。
- **客户端能力**：WakeLock、navigator.vibrate、WebAudio 合成蜂鸣（归零长鸣/进节双响/暂停短促）、canvas 导出 PNG。
- **本地开发**：`npm run test:e2e` 自动应用本地迁移、启动 `wrangler dev`，用真实 HTTP + 本地 D1 跑 `dev/d1-check.mjs`；`npm test` 七张网跑内存假库/静态源码，零云依赖。

## 12. 风险

- **Deno 本地是否可用**：不阻塞——本地逻辑验证走 Node 假库；部署后真实请求兜底。
- **匿名写策略审核**：若平台对 anon 写有限制，降级方案是房间码持有制 + 数据卡只读，不推翻架构。
- **canvas 中文渲染**：系统字体本地绘制，无跨域污染问题。
