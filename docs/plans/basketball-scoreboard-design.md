# 篮球计分板 · 设计文档

日期：2026-09-24 ｜ 状态：已逐节确认，待实现 ｜ 项目：Qoder Site（E:\CodingXM\测试）

## 1. 产品定位

**一句话**：校园班赛的官方记分牌——手机当遥控器，任何一块屏幕当大屏，打完自动出一张能甩进班群的数据卡。

**真实痛点**：班赛没有计分板，比分记在某个人的手机备忘录里，打完吵架"到底几比几"，第四节最后两分钟没人记得清犯规。产品价值全部押在**双端同步**和**大屏可读性**上，不押在功能数量上。

**目标用户**：班赛的记分员（学生，非专业）、场上球员、场边围观同学。

## 2. 已确认决策清单

| 决策点 | 结论 | 理由 |
|---|---|---|
| 使用场景 | 校园班赛现场，双端架构 | 唯一让产品"真有用"的场景 |
| 产品边界 | 单场闭环 + 赛后数据卡；预留赛事扩展 | 班赛90%需求在此；赛事系统（报名/赛程/积分榜）明确不做 |
| 统计深度 | 球队级为底，「记录球员得分」建赛时可选开关，默认关 | 省事的人直接打，想发数据卡的人勾上 |
| 规则默认值 | 4节×10分钟、单节团队犯规满5次罚球、每队3次暂停、24秒默认关、平局自动加时 | 班赛友好默认值，建赛时可改 |
| 视觉 | 转播风格 + 球队色彩驱动，纯 CSS 画 LED | 三米外看清比分是第一性能；每场界面由两队队色生成 |
| 同步 | 客户端只发"意图"，服务端原子算状态；1秒轮询 | 防并发丢分；比分晚1秒无感 |
| 时钟 | 不跑在服务端，存 `running+since`，各端本地推算 | 刷新/换机/断网重连不丢时钟 |
| 归零处理 | 自动蜂鸣+进节间休息，不等确认 | 学生记分员手忙脚乱，少一步是一步 |
| 撤销 | 只撤最近一步 | 误按都是刚发生的，多步历史诱发混乱 |
| 登录 | 不做。4位房间码即分享即加入 | 班赛搞账号体系是自嗨 |
| 防锁屏 | 控制端 WakeLock | 记分员不可能打一节亮一次屏 |
| 数据卡存图 | 纯前端 canvas 导出 PNG，不过服务器 | 这是"发班群"的嗨点，且不增加后端负担 |

**明确不做（YAGNI）**：赛事报名/赛程/积分榜/淘汰签表、球员篮板助攻等完整技术统计、多场地并轮、回放挑战、账号体系、WebSocket 长连接、历史比赛列表页（链接即档案）。

## 3. 核心流程

```
建赛（手机 30 秒）
  队名/队色/赛制/犯规上限/暂停数/24秒开关/球员名单开关
  → POST create → 房间码 4K7P + 二维码
        │
        ├─▶ 大屏（笔记本/电视扫码）→ GET /room/4K7P/display → 每秒轮询，只读
        │
        └─▶ 控制端（记分员手机）→ /room/4K7P/control
              比赛中所有动作 → POST apply{意图} → 服务端算状态 → 两端各自轮询到
              │
              └─▶ 结束比赛 → 状态锁定 → /room/4K7P/card 数据卡 → 存 PNG / 复制链接
```

## 4. 界面规格

### 4.1 视觉系统（转播风格）

- **背景**：`#0A0E1A` 深黑蓝。两队队色以斜切面板（`clip-path` 平行四边形）铺在左右，中央留出时钟区。
- **LED 数字**：纯 CSS 自绘七段数码管（每数字 7 个 `clip-path` 段，亮段带同色辉光，灭段 8% 透明度残留）。零字体文件、零图片，任何分辨率清晰。这是产品的视觉签名。
- **字体**：`system-ui` 粗体用于队名/标签；数字一律走 LED 组件。
- **状态色**：BONUS = 红色脉冲；暂停 = 琥珀色；归零 = 全屏红闪 2 次；信号弱 = 整体降饱和 + 灰角标。
- **色盲友好**：颜色永远配合文字标签（"主队/客队"+队名），不单独用颜色编码。
- 三张 AI 风格图（本地 `vibe_images/`，未纳入版本库）仅为方向参考，不进入产品。

### 4.2 建赛页 `/`

队名A/B（必填）+ 取色器（12 预设色板 + 自定义）；赛制 2/4 节 × 5/10/12/15 分钟；单节犯规上限（默认5）；暂停数（默认3）；24秒开关（默认关）；「记录球员得分」开关（默认关，开启后出现两队球员名单输入）。提交后进入**房间页**：大号房间码 + 二维码 + 两个按钮（打开大屏 / 打开遥控器）。

### 4.3 控制端 `/room/:code/control`（手机竖屏，单手拇指区）

```
┌─────────────────────────┐
│ 4K7P ●在线        ↩撤销 │
│ Q2  07:32     [⏸/▶]  ▶红│
├─────────────────────────┤
│ 🔴计算机1班        48   │
│ [张伟][李强][王芳]       │
│  +1    +2    +3         │
│  犯规+1      暂停-1      │
├─────────────────────────┤
│ 🔵软件工程2班     47    │
│  +1    +2    +3         │
│  犯规+1      暂停-1      │
├─────────────────────────┤
│ [下一节 ▶]   [🏁结束比赛]│
└─────────────────────────┘
```

- **球员 Chip 是选中态**：点某人高亮，此时 +1/+2/+3 记到该球员；再点取消回到球队级。选中态常驻可见防误按。
- 按钮 ≥56px、高对比（户外阳光下可读）；每次成功写入触发 `navigator.vibrate(15)` 震动反馈。
- 顶部状态条：连接状态（●在线 / ⚠N个待发送 / 冲突提示）+ 撤销按钮（撤完置灰 1 秒）。
- WakeLock 常亮；切后台自动让位，回前台重拿并立即同步。
- 键盘快捷键（笔记本当控制端时）：`空格` 开始/暂停，`Z` 撤销，`A/S/D` 主队+1/+2/+3，`J/K/L` 客队+1/+2/+3。

### 4.4 大屏展示端 `/room/:code/display`（16:9 投影优先）

```
┌──────────────────────────────────┐
│ Q2        07:32        ● 直播     │
│ ┌───────────┐     ┌───────────┐  │
│ │ 计算机1班 │48:47│软件工程2班│  │
│ │ ●●○ 暂停2 │     │ 暂停3 ●●● │  │
│ │ 犯规 3/5  │     │ 犯规 4/5  │  │
│ └───────────┘     └───────────┘  │
│   BONUS 红队罚球     ▶进攻 红     │
└──────────────────────────────────┘
```

只读、零操作。节间休息/暂停自动切全屏倒计时画面。已结束自动跳数据卡。

### 4.5 数据卡 `/room/:code/card`（3:4，适合群聊）

终比分 + 获胜标记、每节得分流水、得分王（开启球员记录时）、三分对比、犯规对比、房间码水印。两个按钮：**保存图片**（canvas 导出 PNG）、**复制链接**。

## 6. 数据模型

单表 `games`，整场状态一个 JSON 文档（读-改-写 + 版本号 CAS 的模型下，规范化拆表只会增加跨请求事务问题）：

```sql
create table games (
  code        text primary key,            -- 4位房间码（字符集去 0O1I）
  status      text not null default 'setup',-- setup|live|break|timeout|finished
  version     integer not null default 0,   -- 每次写 +1，CAS 用
  state       jsonb not null,               -- 见下
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now()
);
-- 预留赛事扩展：以后加 tournament_id 列，不动结构
```

`state` 结构：

```jsonc
{
  "config": { "periods":4, "periodMinutes":10, "overtimeMinutes":5,
              "foulLimit":5, "timeouts":3, "timeoutSeconds":60,
              "shotClock":false, "shotClockSeconds":24,
              "trackPlayers":false, "breakSeconds":120 },
  "teams": [ { "name":"计算机1班", "color":"#1E4FD8", "score":48,
               "fouls":3, "timeoutsLeft":2,
               "periodScores":[12,14,13,9], "stats":{"pts3":6,"pts2":15,"pts1":6} }, ... ],
  "players": [ { "team":0, "name":"张伟", "points":15 } ],
  "clock":   { "mode":"game", "period":2, "running":true,
               "since":"…", "remainingMs":452300, "gameRemainingMs":452300,
               "timeoutTeam":null },
  "shot":    { "running":false, "since":null, "remainingMs":24000 },
  "possession": 0,
  "undo":    { /* 上一步快照：teams/players/clock/shot/possession，仅一层 */ },
  "startedAt":"…", "finishedAt":null, "winner":null
}
```

**时钟推算（各端一致）**：`mode=game` 且 `running` 时，显示值 = `remainingMs - (now - since)`；停止时显示 `remainingMs`。暂停/节间用 `mode` 切换，比赛时钟冻结在 `gameRemainingMs`。

## 7. 同步与动作模型

```
客户端                          Worker (handler)                  D1
  │ POST apply{code,version,意图} ─▶ 读 state+version
  │                                 CAS: update where version=期望
  │                                 0行受影响 → 重读重放（≤3次）→ 仍冲突返回409
  │ ◀─ 新 state+version ────────────┘
  │ GET get&code ─▶ {state, version, serverTime}   （两端各自每秒轮询）
```

- **意图白名单**：`score{team,points,playerId?}`、`foul{team}`、`timeout{team}`、`clock_start/stop`、`shot_reset`、`possession{team}`、`period_next`、`clock_zero`（归零自动进节）、`break_end`、`undo`、`finish`、`reset`。未知动作 400。所有意图带客户端生成的 `nonce`。
- **幂等键（对抗审查补）**：户外丢包时客户端会补发同一意图，服务端按 `nonce` 去重（每场保留最近 30 个），重复意图只记一次且不涨版本。没有这一条，一次信号抖动就能凭空多算 2 分。
- **模式门禁（对抗审查补）**：记分/记犯规只在 `clock.mode==='game'` 时接受——休息期按 +3 会静默记进下一节的流水，属于数据污染；叫暂停还要求 `status==='live'`，否则未开打就能烧掉一次暂停。
- **无变化不写库**：应用后状态与之前等价（如重复上报归零）直接返回当前状态，不涨版本，避免多端同时上报造成无意义 CAS 冲突。
- **休息中按"下一节"= 提前结束休息**（班赛休息期常提前开打），不再报错。
- **服务端规则引擎**：得分→队/球员分数+节流水+三分计数+进攻箭头转向；犯规→满 `foulLimit` 置 BONUS；`clock_zero`→进节间休息（新一节犯规清零）；末节平局→自动加时，**末节分出胜负必须结束**（不得无限加时）；`finish`→锁定、算 winner（平局为 null，不误判主队）。
- **严格整数**：`team`/`points` 只接受真正的整数，拒绝 `null`/`"2"`——`Number(null)===0` 会把脏输入静默变成"主队加 0 号位"。
- **断网**：控制端动作进本地队列（localStorage 持久化），按序补发；大屏 >3 秒无响应显示"信号弱·最后更新 HH:MM"并冻结时钟显示。
- **房间码**：字符集 `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`（去易混 0O1I），4 位 ≈ 100 万组合，创建时查重。
- **清理**：平台无 cron。创建新房间时顺带删除 `status=setup 且超 24h` 的废弃房间；已打完的房间永久保留（数据卡链接要能长期打开）。

## 8. 异常状态矩阵

| 状况 | 表现 | 恢复 |
|---|---|---|
| 房间码不存在 | "房间不存在或已归档"+新建引导 | 检查码/新建 |
| 控制端断网 | 角标"⚠N个待发送"，按钮仍响应（本地乐观+队列） | 恢复按序补发 |
| 大屏断网 | 灰角标"信号弱·最后更新 19:42"，时钟静止不显示假时间 | 轮询恢复自动续 |
| 时钟归零 | WebAudio 合成蜂鸣+全屏红闪，自动进节间休息 | 休息归零自动进下一节 |
| 并发写冲突 | 服务端重放成功则静默；失败提示"状态已变化，已刷新" | 重新拉取 |
| 撤销后 | 按钮置灰 1 秒 | — |
| 手机切后台 | WakeLock 让位 | 回前台重拿+立即同步 |
| 已结束 | 控制端只读+数据卡入口 | `reset` 重开一场 |
| 存图失败 | 提示"请截图保存" | 降级可用 |

## 9. 技术选型与部署契约

**部署平台变更记录（2026-09-24）**：首版按 Qoder Sites（静态 + Edge Function + Supabase 适配器）实现并本地验证通过，但平台侧建站请求持续返回通用失败，云资源无法分配；同日改投 **Cloudflare Workers + D1** 并完成部署与线上验证。规则引擎与前端一行未动，只替换了数据访问层——这验证了当初"handler 只依赖注入的 store 接口"的分层是对的。

- **前端**：纯静态 SPA（原生 ES modules，无框架无构建），目录 `public/`，由 Workers Assets 托管，SPA 回退用 `not_found_handling: single-page-application`。
- **服务端**：`worker/index.js` 为 Workers 入口，`/api/*` 走业务 handler，其余交给静态资源绑定。业务层 `worker/handler.mjs` 只依赖 store 接口（`getGame / insertGame / casUpdateGame / deleteStaleSetup`）。
- **数据库**：Cloudflare D1（SQLite）。整场状态一个 JSON 文本列 + `version` 列；并发写用 `UPDATE ... WHERE code = ? AND version = ?` 的**影响行数**判定 CAS，这是真实 SQL 语义，不是内存假库的模拟。
- **客户端能力**：WakeLock、navigator.vibrate、WebAudio 合成蜂鸣（归零长鸣/进节双响/暂停短促）、canvas 导出 PNG。
- **本地开发**：`wrangler dev`（本地 D1 仿真）跑真实链路；`npm test` 三张网跑内存假库，零云依赖。

## 10. 验收标准与实测结果

1. 建赛→房间码→二维码渲染正确 —— 浏览器实测通过
2. 控制端 +2 → 大屏 ≤1.5s 显示新比分 —— 实测通过（含选人归属）
3. 时钟跑动中刷新大屏/换设备 → 时间连续不跳 —— 实测通过
4. 犯规到 5 → BONUS 亮；进下一节 → 犯规清零 —— 实测通过
5. 撤销回退一步；置灰生效 —— 实测通过
6. 归零 → 蜂鸣+红闪+自动节间→自动进下一节；末节平局自动加时 —— 规则层实测通过
7. 结束 → 数据卡数字与过程一致 → 存 PNG 成功 —— 实测通过（1080×1440 / 168KB）
8. 断网操作排队、恢复补发不丢分且不重复计分 —— 幂等键实测（请求体带 nonce）
9. 错误房间码 → 友好提示 —— 实测通过
10. 部署后真实请求验证 —— **已完成**：`node dev/d1-check.mjs <线上地址>` 对 Cloudflare 生产环境 27/27 通过（含真 SQL CAS、幂等 noop、并发双写、SPA 深链、no-store），并在浏览器中确认跨进程写入经轮询反映到大屏

**测试网（本地）**：`node dev/smoke.mjs` 27 项主流程；`node dev/attack.mjs` 60 项对抗探针（幂等、并发、跳节滥用、类型强制、不可逆性、无界增长、注入面、协议健壮性、胜负判定）；`node dev/mutate.mjs` 15 个变异体全部被击杀（证明每条断言都不是空断言）。

**对抗审查净新增的修复**：幂等键缺失（响应丢失补发会双计）、休息/暂停期间记分串节、未开打可烧暂停、`Number()` 静默吞脏输入、无变化写库涨版本造成冲突风暴、休息中无法提前开打、控制端不显示剩余暂停。

## 11. 实现里程碑

M1 骨架+视觉系统（LED 数字、队色面板、路由）→ M2 Function+schema+假库全链路 → M3 建赛/房间页 → M4 控制端 → M5 大屏 → M6 数据卡 → M7 异常矩阵+响应式打磨 → M8 本地验证 → 发布。

## 12. 风险

- **Deno 本地是否可用**：不阻塞——本地逻辑验证走 Node 假库；部署后真实请求兜底。
- **匿名写策略审核**：若平台对 anon 写有限制，降级方案是房间码持有制 + 数据卡只读，不推翻架构。
- **canvas 中文渲染**：系统字体本地绘制，无跨域污染问题。
