# 篮球计分板 · Basketball Scoreboard

> 校园班赛的官方记分牌：手机当遥控器，任何一块屏幕当大屏，打完自动出一张能甩进班群的数据卡。

**在线使用**：https://score.tryworld.com.cn （无需注册，打开即是建赛页）

> `*.workers.dev` 子域在国内网络下会被 DNS 污染、间歇性不可达，所以线上走自定义域名 `score.tryworld.com.cn`（Cloudflare zone 权威 DNS）。原始的 workers.dev 地址仍可用：https://basketball-scoreboard.1822520752.workers.dev

## 为什么做这个

班赛现场的真实痛点不是"没有计分 App"，而是：**比分记在某个人的手机里，打完吵架，第四节最后两分钟没人记得清犯规**。

所以这个项目的全部价值押在两件事上，而不是功能数量：

1. **双端同步** —— 记分员用手机点，全场看大屏，谁都不用抢那台手机
2. **大屏可读性** —— 三米外一眼看清比分，这是计分板的第一性能

## 核心特性

| | |
|---|---|
| 📱 **手机遥控 + 大屏展示** | 4 位房间码即分享即加入，扫码或点链接都行，**没有注册登录** |
| 📺 **转播风格大屏** | 纯 CSS 手绘七段数码管（零字体、零图片），界面由两队队色生成 |
| ⏱ **时钟不丢** | 服务端只存"正在走、从某时刻起剩多少"，刷新 / 换设备 / 断网重连后时钟连续 |
| 🛡 **不丢分也不双计** | 客户端只发"意图"，服务端原子算状态；两个记分员同时按分都算；响应丢失后补发只记一次 |
| 🏷 **改过分可核对** | 每一次落地都留审计（谁/何时/从几分改成几分），赛后数据卡页公开可查——打完吵架对账用 |
| 🏆 **赛后数据卡** | 每节流水、得分王、三分/两分/罚球/犯规对比，**一键存 1080×1440 PNG**（纯前端 canvas，不过服务器） |
| 📴 **户外弱网可用** | 断网时得分/犯规排队，恢复后按序补发；撤销、终局等时刻敏感操作必须联网才发；待发送列表常驻可见；大屏显示"信号弱·最后更新 HH:MM"而不是假时间 |
| ⌨ **笔记本也能当遥控器** | `空格` 开始/暂停、`Z` 撤销、`A/S/D` 与 `J/K/L` 主队/客队 1/2/3 分、`R` 重置 24 秒、`P` 交换球权 |

## 快速开始

```bash
npm install                 # 只装 wrangler，运行时零依赖
npm run db:migrate:local    # 本地 D1 建表
npm run dev                 # http://127.0.0.1:8787
```

打开后点「新建比赛」→ 填两队队名与队色 → 再开一个标签页访问 `/room/<房间码>/display` 就能看到双端同步。

> **控制凭证**：创建成功时服务端只回一次控制令牌，之后只留在创建比赛的那台设备上。房间码给所有人**读**（大屏 / 数据卡 / 操作记录），改比分必须持令牌——用创建比赛的手机打开遥控器即可；要在别的设备上遥控，回房间页点「复制控制端链接」。同时还会拿到一个 **8 位找回码**：创建比赛的手机丢了（换机 / 清缓存），凭「房间码 + 找回码」在首页换发新的控制令牌，旧令牌与旧找回码同时作废。读取照常，写路径需要重新建赛的情况从此消失。

> **不想接 Cloudflare？** `npm test` 七张测试网跑在内存假库上，不需要任何云账号或网络。

## 架构

```
浏览器（原生 ES module，无框架无构建）
  ├─ /                    建赛 · 加入
  ├─ /room/:code          房间码 + 二维码
  ├─ /room/:code/control  控制端（手机）
  ├─ /room/:code/display  大屏（只读）
  └─ /room/:code/card     数据卡（canvas 导出 PNG + 操作记录核对）
        │
        │  同源 /api/game?action=get|create|apply|log|recover
        ▼
Cloudflare Worker
  worker/index.js      入口：/api/* 走业务 handler，其余交静态资源；统一安全响应头；cron 每分钟到点推进
  worker/handler.mjs   参数校验 · 意图白名单 · 版本号 CAS 重放 · 控制凭证校验 · 操作审计 · 到点推进 · 失败限流
  worker/rules.mjs     规则引擎（纯函数，比分/时钟/犯规/节次唯一事实来源）
  worker/ratelimit.mjs 进程内滑动窗口限流（只挡失败请求，不挡正常轮询）
  worker/store-d1.mjs  D1 适配器（换库只动这一层）
        ▼
Cloudflare D1   games 表：一场比赛一行，整场状态一个 JSON + version
                action_receipts 表：nonce 幂等回执（与 games 级联）
                action_log 表：操作审计——谁/何时/什么动作/比分从多少改成多少（与 games 级联）
```

**三条撑起其余一切的设计决定：**

1. **客户端只发"意图"，服务端算状态。** 手机发的是"红队 +2"，不是"新比分=48"。否则两个人同时按 +1 必然丢一个，而且谁能改比分这事必须握在服务端。
2. **时钟不跑在服务端。** 只存 `running + since + remainingMs`，任何设备打开都能自己推算当前剩余——刷新、换手机、断网重连，时钟都不丢。
3. **1 秒轮询，不做 WebSocket。** 比分晚一秒出现毫无感知（真实记分牌本来就是裁判吹哨后才变），换来零长连接基础设施、断线自动恢复。

完整设计推演（含逐条决策理由与异常状态矩阵）见 [`docs/plans/basketball-scoreboard-design.md`](docs/plans/basketball-scoreboard-design.md)。

## 规则默认值

4 节 × 10 分钟、单节团队犯规满 5 次起罚球、每队 3 次暂停、24 秒进攻时限默认关、末节平局自动进加时、时钟归零自动进节间休息并蜂鸣。建赛页可改节数、每节时长、犯规上限、暂停数、24 秒开关和球员记录；加时/暂停/节间时长保留服务端默认值。撤销只撤最近一步——误按都是刚发生的，多步历史反而诱发"回到五分钟前"的混乱。

开启 24 秒后：开球即走表，**进球归满并继续走**（不是停表），暂停/停表同步停；归零蜂鸣并自动重置，球权用「⇄ 交换球权」手动切。
撤销会同时把时钟停在动作发生那一刻（不自动继续走）——这是刻意的：让撤销悄悄吞掉停表时间，比多按一次「开始」危险得多。

「下一节 ▶」在**末节已分胜负**时会直接终局并锁定比分，因此这一下和「结束比赛」一样要先确认（平局会进加时、节间休息中只是提前结束休息，都不问）。 Clock自然走完导致的终局没有确认可弹，那是比赛正常打完。

## 部署到自己的 Cloudflare

```bash
npx wrangler d1 create scoreboard-db          # 把返回的 database_id 填进 wrangler.jsonc
npx wrangler d1 migrations apply scoreboard-db --remote
npx wrangler deploy
```

> **顺序不能反**：Worker 的读路径会查 `controller_hash` 列，回执写路径还需要 `receipt_id`，审计写路径要 `action_log` 表，找回码要 `recovery_hash` 列（`migrations/0002` + `0003` + `0004` + `0005`）。先部署后迁移 = 所有请求 503。Workers Builds 自动部署不会替你跑迁移——每次改了 `migrations/` 都要先手动 apply 再推代码。

### 推送即自动部署

用 Cloudflare 原生的 **Workers Builds** 接 GitHub：Worker 详情页 → Settings → Builds →
Connect to Git，选本仓库、生产分支 `main`。此后每次 push 到 `main` 自动构建并部署，
**GitHub 侧不需要存任何凭据**（Cloudflare 自己管），PR 还会自动带上预览链接。

`.github/workflows/test.yml` 只负责把七张测试网当合并门禁跑一遍，不参与部署。
建库和迁移仍按上面的命令手动执行——Workers Builds 不会替你跑 D1 迁移。

### 本地真实 D1 门禁

```bash
npm run test:e2e
```

该命令会执行本地迁移，启动临时 `wrangler dev`，再用真实 HTTP + 本地 D1 跑 `dev/d1-check.mjs`，结束后自动关闭 Worker。它不读取 Cloudflare 凭据，也不会触碰生产库；CI 的 `local-d1` job 跑的是同一条命令。当前真实 SQL 链路共 35 项（含静态响应安全头、cron 到点推进、控制权补发）。远程验证必须显式设置 `D1_CHECK_ALLOW_REMOTE=1`，防止误把写探针打到生产。

## 技术栈

Cloudflare Workers · D1 · 原生 ES Module · Web Audio（合成蜂鸣，无音频文件）· WakeLock（防锁屏）· Canvas（数据卡导出）· wrangler

**运行时零依赖**：前端没有框架和构建步骤，后端没有第三方包。`@playwright/test` 只是 devDependency，仅供可选的 `npm run test:ui` 真浏览器门禁使用，不进运行时。

## 已知边界

- **房间码只给读，改比分要控制凭证**。创建比赛时服务端签发一次性控制令牌（库里只存 SHA-256），此后只有持令牌的设备能写。拿到 4 位房间码可以看大屏、看数据卡、看操作记录，但改不了比分——这是班赛的刻意取舍（现场要的是快，不是权限）。**手机丢了有救**：建赛时会同时拿到一个 8 位找回码，凭「房间码 + 找回码」在首页即可换发新的控制令牌（换发即换锁：旧令牌和旧找回码同时作废，当初截屏流落到班群里的旧码从此失效）。找回码只在建赛/换发响应里明文出现一次，请截图或发到自己微信——只存在创建比赛的那台设备上等于没救。要用于正式比赛，需要加裁判身份与签名写路径。
- **操作审计是公开读的**。`action=log` 和读比分一样只凭房间码——班里任何人拿到码都能核对「谁在什么时候把比分从多少改成多少」，这是它防吵架的方式。审计只记**真落地**的改动：被规则拒绝的动作、幂等拦下的补发、无变化的动作都不留痕；`reset` 重开不清旧日志（终局被擦掉这件事本身必须可查）。操作者只存凭证指纹（哈希前 8 位），不存令牌本身；控制权补发在审计里记为 `actor=recovery`。
- **迁移前的老比赛变为只读**。`migrations/0002` 之前的房间没有凭证字段，一律 fail closed：数据卡链接照常打开，但不能继续遥控。`migrations/0003` 只给回执增加 attempt marker，`migrations/0004` 增加操作审计表，都不影响已结束数据卡。进行中的老局请在部署前打完。
- **限流是尽力而为，不是硬保证**。Workers 没有跨请求共享内存，计数器按 isolate 独立：能显著抬高"遍历 4 位房间码"的成本，挡不住分布式枚举。只统计失败请求（房间不存在 / 参数非法 / 冲突 / 凭证不符），正常 1 秒轮询不计次、不会被误伤。
- 已结束的比赛永久留在库里（数据卡链接要能长期打开）；"筹建中但没打"的房间、以及超过 7 天没有任何写入的半途放弃局，在下次建赛时顺带清理（清理仍挂在建赛上；每分钟的 cron 只做「到点推进时钟」，不碰清理）。
- **到点推进不依赖记分员的手机**。cron 每分钟把「时钟已归零但没人上报」的比赛推进一步（进节间 / 收回暂停 / 摆好下一节停表等开始），和记分员自己上报走同一套规则，撞车时 CAS 保证只有一个生效。但**开表、记分这些动作仍然只有控制端能发**——cron 只会把该到的时刻推到，不会代替任何人操作。24 秒违例的自动归满也仍由控制端负责（它跟着比赛时钟走，控制端恢复后自然续上）。
- 撤销只撤最近一步，且撤销会同时停表——这是为了不让时间在记分员看不见的地方被消耗掉。
- 数据卡存图依赖浏览器 canvas 导出中文字体，个别环境失败时会提示改用截图。
